# Session notes — 2026-04-22

Hard-won learnings from the video-playback rework and the HDMI-blackout cron.

## mpv quirks on this Pi

### `--keep-open=always` suppresses `end-file`

With `--keep-open=always`, mpv does **not** emit an `end-file` event at natural
EOF. Instead it pauses on the last frame and flips the `eof-reached` property
to `True`. The original event-based detection in `player.py` never fired; the
`_dwell` loop would sit forever waiting for EOF.

**Fix:** listen for `property-change { name: "eof-reached", data: true }`
instead of `end-file`. The observer was already registered in
`Player.start()` — the event handler just needed to key off it.

### `--keep-open=always` pause state persists across `loadfile replace`

When mpv pauses at EOF, calling `loadfile ... replace` loads the new file
but inherits the pause. The new file sits frozen on frame 0 and never
progresses — no `eof-reached` transition, no forward motion.

**Fix:** send `set_property pause false` from the `playback-restart`
handler (once per loaded file). Doing it *before* `loadfile` doesn't
stick because mpv re-pauses during the load.

### `eof-reached` lies briefly during loadfile transitions

Between the old file ending and the new file starting, `eof-reached` can
flip `True` momentarily as a side effect of the replace. A naive listener
sees "the video just finished" ~0 ms after load.

**Fix:** gate the EOF signal on a `_playing` flag that is set by
`playback-restart` and cleared by `show()`. Only the first `eof-reached=true`
*after* playback actually started counts.

### Reader-thread deadlock on synchronous commands

`MpvClient.command()` blocks waiting for mpv's reply on a queue. The reply
arrives via the reader thread. If you call `command()` from inside
`_on_event` (which runs on the reader thread), the reply can never be
delivered — the thread is blocked waiting for itself. Manifested as a
15 s `TimeoutError` from `set_property("osd-msg1", ...)` on every
`playback-restart`.

**Fix:** added `MpvClient.command_async()` — fire-and-forget, no
`request_id`, no waiter. Used for both the caption update and the unpause
from the event handler.

### Video playback is noticeably slower than real-time

On this Pi 3B with `hwdec=v4l2m2m-copy`, an 11.07 s video file takes
~17 s wall time to play. Matters for the "loop short videos until
`slide_seconds`" rule: a file the user thinks should loop (11 s < 20 s)
might not, because the first play already crosses 20 s. Implementation
tracks wall-clock, which is the honest signal — the user's mental model
just has to account for the Pi being slow.

## Video count: videos are rare

Out of 5559 indexed media files, **only 20 are videos** (0.36 %). Hitting
one via random `/next` advances is impractical — for targeted testing use
a standalone harness (`tools/test_video_dwell.py`) that drives `Player`
directly against a known path. Requires stopping the service to free
the IPC socket.

- Cold walk of 5559 files: ~7 s.
- Metadata refresh (EXIF/IPTC via exiftool): adds ~65 s.
- Total cold start: ~72 s between "service starting" and "web UI at …".
- Warm restart is the same — cache is by mtime, not session.

## Web UI controls

- **Ban current** → appends to `/home/pi/claudeframe/banned.txt`, filtered
  out of `indexer.items()` on read, no rescan required. File stays on disk.
- **Rescan** triggers `_rescan` flag. The flag is checked once per dwell
  iteration, so the scan runs between slides (or ~0.25 s polling during a
  video). Cached metadata is reused — incremental rescans are cheap.
- Rescans also fire automatically at startup and from the `inotify`
  watcher on `/home/pi/Frame` (recursive, debounced 2 s). Note: inotify
  does not see changes made *remotely* on a CIFS-mounted NAS — only local
  FS events.

## HDMI blackout

`vcgencmd display_power 0|1` toggles the HDMI signal — most monitors go
to standby. Lightweight, no X11 required. Cron on the Pi (pi user):

```
0 1 * * * /usr/bin/vcgencmd display_power 0 >/dev/null
0 6 * * * /usr/bin/vcgencmd display_power 1 >/dev/null
```

Timezone is `America/New_York` so entries fire at local time. The
claudeframe service keeps running through the blackout; slides still
advance, just to a dark screen.
